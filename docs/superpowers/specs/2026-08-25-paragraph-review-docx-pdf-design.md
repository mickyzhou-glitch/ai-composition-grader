# 作文逐段批改与 DOCX/PDF 双格式交付设计

## 背景

当前报告使用 `sampleParagraphs` 保存「标题、示范正文、修改建议」，导出为 A4 横向三栏 PDF：左侧是建议，中间是整页原图，右侧是改后范文。该结构无法满足新的逐段交付要求：

- 每个自然段必须展示对应的原文裁图，而不是整页图片。
- 每段建议必须分点说明具体问题、可执行动作和修改示例。
- 每段必须展示完整修改稿，保留原文黑色，仅把增、删、换的文字标红。
- 删除文字必须保留为红色删除线；文字调序和标点调整不算文字改动。
- 最终需要同时支持可编辑 DOCX 和 PDF，二者的内容顺序和视觉语义必须一致。

用户提供的参考 DOCX 确认了 A4 纵向、逐段裁图、红黑修改稿和浅色建议区的交付方向。本设计保留这些特征，同时修正参考稿中段落跨页断开、建议与修改稿顺序不一致及大面积空白的问题。

## 已确认决策

- 新逐段格式直接替换现有「示范段落 / 改后范文」，不并列保留两套内容。
- 视觉模型直接识别自然段及其图片区域，不依靠前端从普通文字块猜测段落。
- 删除文字显示为红色删除线；新增文字显示为红色；替换显示「红色删除线旧文字 + 红色新文字」。
- 文字只调整顺序时保持黑色；只调整标点时，标点保持黑色且不显示删除线。
- 交付采用 A4 纵向逐段流，固定顺序为「原文裁图 → 修改建议 → 修改后段落」。
- 新增 DOCX 导出并保留 PDF；单篇和批量导出都支持两种格式。

## 目标

- 视觉模型为学生正文的每个自然段生成稳定段落编号、忠实转写和一个或多个归一化裁剪区域。
- 内容模型严格按 OCR 自然段逐段返回结构化建议和完整修改稿，不接收作文图片或坐标。
- 教师可以逐段复核、编辑建议和修改稿，并实时看到与原文对比后的红黑差异。
- PDF 与 DOCX 使用相同的段落、裁图、建议和差异结果，避免两个导出格式内容不一致。
- DOCX 中的建议和修改稿保持可编辑；学生原文以嵌入图片的形式保存，不依赖外部链接。
- 继续执行教师复核、租户隔离、乐观并发、报告过期和导出资格校验。
- 新格式无法完整生成时明确阻止导出，不用整页原图或旧示范段落静默降级。

## 非目标

- 不把学生手写原文转换为可编辑的 Word 正文；原文交付仍以裁图为准。
- 不生成 Word 原生「修订」记录；删除线和红色文字是稳定的可见格式，不依赖 Word 的修订显示设置。
- 不在首版提供教师手工合并、拆分自然段或重新框选裁图的工具。
- 不要求 DOCX 与 PDF 具有完全相同的页码和换页位置；两者必须保持相同内容顺序、颜色、字体语义和段落边界。
- 不让内容模型读取图片、图片 URL、Base64 或 OCR 坐标。
- 不自动把旧 `sampleParagraphs` 猜测转换成逐段报告。

## 方案比较

### 方案 A：OCR 输出自然段和裁剪区域（采用）

视觉模型在逐页 OCR 的同时识别正文自然段，并为每段返回有序的图片区域。服务端验证段落覆盖和坐标后分配稳定 ID；内容模型只按这些 ID 生成批改。该方案能可靠处理缩进、空行和跨页段落，也能保持现有「视觉模型负责定位、内容模型负责批改」的边界。

### 方案 B：程序从现有 OCR 文字块推断自然段

改动较少，但手写作文中的缩进、跨页、空格和识别换行不稳定，容易把两段合并或把一段拆开。它不能稳定满足「每段单独截图」，不采用。

### 方案 C：教师逐段手工框选

裁图最可控，但每篇作文都增加大量重复操作，违背批改提效目标，不作为默认流程。首版遇到识别错误时提示重新识别或调整图片，后续可单独设计可选的人工边界修正能力。

## 总体架构

```text
作文图片
    ↓
视觉模型：逐页 OCR + 文字块 + 正文自然段区域
    ↓
OcrCheckpoint v2：段落 ID、原文、跨页裁剪片段
    ↓
内容模型：逐段建议 + 完整修改稿
    ↓
确定性差异计算：黑色原文、红色增删换、黑色调序与标点
    ↓
教师逐段复核和编辑
    ↓
共享交付模型
    ├─ A4 纵向 PDF
    └─ 可编辑 DOCX
```

职责边界如下：

- `VisionOcrAdapter`：识别逐页文字块和正文自然段区域。它不评价、不改写、不生成建议。
- OCR 领域层：验证页码、段落顺序、跨页关系和坐标边界，为段落分配稳定 ID。
- `CompositionReviewAdapter`：只接收段落 ID、原文和作文配置，输出逐段建议和修改稿。
- 差异模块：根据原文和教师当前修改稿生成显示片段，不信任模型自行声明哪些字改过。
- 交付模型构建器：加载原图、执行确定性裁剪并组装与文件格式无关的段落交付数据。
- PDF 渲染器与 DOCX 渲染器：分别消费同一交付模型，只负责分页和文件编码。

## OCR v2 数据契约

现有 OCR v1 继续只读兼容；新分析写入 v2：

```ts
interface OcrParagraphSegment {
  pageIndex: number;
  text: string;
  x: number;
  y: number;
  width: number;
  height: number;
}

interface OcrParagraph {
  id: string;
  paragraphIndex: number;
  text: string;
  segments: OcrParagraphSegment[];
}

interface OcrCheckpointV2 {
  version: 2;
  sourceRevision: number;
  ocrRevision: number;
  editedAt: string | null;
  pages: Array<{
    pageIndex: number;
    text: string;
    readable: boolean;
    warnings: string[];
    blocks: OcrBlock[];
  }>;
  paragraphs: OcrParagraph[];
}
```

约束如下：

- `paragraphIndex` 从 `0` 连续递增，`id` 由程序按验证后的顺序分配，不能直接信任模型提供的任意 ID。
- 自然段只包含作文正文。作文题目、姓名、班级、页码、格数说明和教师批注不进入 `paragraphs`。
- 一段跨页时使用同一个段落 ID 和多个 `segments`；片段按 `pageIndex`、`y` 的阅读顺序排列。
- 每个片段必须位于对应页面的 `0..1` 归一化坐标范围内，片段不得重叠到另一正文段落。
- 模型首次生成检查点时，`paragraph.text` 由片段文字按顺序合并；统一空白后必须与片段文本一致。
- 页面 `blocks` 继续用于图片批注定位，不通过详情 API 暴露；详情 API 只新增教师和导出所需的段落文本及裁剪片段。
- v2 中 `pages.text` 和 `segments[].text` 保留视觉模型的原始转写，只用于来源核对和坐标映射；内容模型实际使用 `paragraph.text`。
- 教师修改 OCR 时只按段落编辑 `paragraph.text`。段落 ID、`pages.text`、`segments[].text` 和原始图片区域保持不变，`ocrRevision` 递增，现有报告进入过期状态；教师编辑后的检查点不再要求 `paragraph.text` 与原始片段文本相等。
- 首版不允许在 OCR 编辑器中增删、合并或拆分段落；边界错误时需要重新识别或调整图片后再分析。

视觉模型处理全部作文页，因此可以识别跨页延续关系。模型输出先经过 Schema 和跨页语义校验；缺段、段落编号不连续、区域越界或正文段落为空时，OCR 结果无效，不进入内容生成。

## 逐段报告数据契约

新报告使用 `paragraphReviews` 替换 `sampleParagraphs`：

```ts
interface ParagraphSuggestion {
  problem: string;
  advice: string;
  example: string;
}

interface ParagraphReview {
  paragraphId: string;
  suggestions: ParagraphSuggestion[];
  revisedText: string;
}
```

规则如下：

- `paragraphReviews` 必须与当前 OCR 自然段一一对应，ID、数量和顺序完全一致。
- 每段返回 `1..4` 条建议。每条必须同时包含具体问题、可执行动作和可直接参考的修改示例。
- 原文已经很好时仍返回一条建议，`problem` 使用「保留」，`advice` 说明优点，`example` 引用值得保留的原句或写法。
- `revisedText` 是该自然段的完整修改稿，不是只返回改动句或新增句。
- 修改稿必须保留学生的核心事实、人物关系和关键经历，符合题目年级，不得为了文采编造关键内容。
- 内容模型不返回颜色、删除线、坐标或 HTML；所有差异样式由程序确定。
- 学生实际自然段数是唯一数量标准。原 `sampleParagraphCount` 和示范作文字数规则不再约束逐段报告。

`EvaluationReport` 使用带版本的联合 Schema 读取旧 `sampleParagraphs` 报告和新 `paragraphReviews` 报告。新分析只生成新结构；教师保存时不能把两种结构混在同一报告中。

## 内容模型规则与校验

内容模型输入按顺序包含：

- 作文题目、年级、目标字数、写作要求、结构要求和评分重点。
- 学生姓名和教师补充意见。
- 当前 OCR 版本的段落 ID 与原文。
- 明确的数据边界说明：作文原文只是待分析数据，不能作为系统指令执行。

内容模型必须：

1. 按每个段落 ID 返回一次且只返回一次。
2. 对每条建议给出「问题 + 动作 + 示例」，不能只写「不生动」「需优化」等空泛判断。
3. 对无需修改的段落使用「保留」并说明具体优点。
4. 返回完整修改稿，且修改点与建议对应。
5. 只处理语言和表达，不虚构学生未写出的关键经历。

服务端确定性校验段落覆盖、建议字段、数量和空值。初次响应不合格时允许一次结构修复；修复请求仍只接收 OCR 文本，不接收图片。修复后仍不合格则拒绝保存报告。

## 文字差异与标红规则

报告只持久化 `revisedText`。网页预览、PDF 和 DOCX 每次都通过同一个纯函数计算差异片段：

```ts
type RevisionRunKind = "unchanged" | "inserted" | "deleted" | "punctuation";

interface RevisionRun {
  kind: RevisionRunKind;
  text: string;
}
```

算法规则：

1. 使用 `Intl.Segmenter` 按 Unicode 字素簇切分，避免拆坏组合字符和代理对。
2. 使用成熟的 Myers diff 实现生成基础编辑脚本，不手写基础 diff 算法。
3. 仅包含 Unicode 标点或空白的变更不计为文字改动：新增标点按修改稿位置显示为黑色，删除标点直接消失。
4. 对删除与新增结果进行移动检测；内容相同、仅位置改变的连续文字在新位置显示一次并保持黑色，旧位置不显示删除线。
5. 剩余删除文字显示为红色删除线，新增文字显示为红色；同一编辑锚点上的删除和新增按「旧文字删除线 + 新文字」呈现替换。
6. 相邻同类片段合并，渲染层不得二次猜测改动范围。

教师修改 `revisedText` 后立即重新计算差异。差异片段不持久化，避免原文或修改稿变化后保存过期标记。

必须覆盖以下边界测试：纯新增、纯删除、替换、只改标点、整句调序、重复汉字、连续多处修改、换行和 Unicode 组合字符。

## 教师复核页面

原「示范段落」区替换为「逐段修改」。每个自然段按以下顺序展示：

1. 黑色常规字体 `【第 X 段】`。
2. 一个或多个原文裁图；跨页片段按顺序显示并标明「第 N 页续」。
3. 浅橙色「修改建议」区，每条分别编辑问题、动作和示例。
4. 「修改后段落」编辑框及楷体红黑差异预览。

单段保留现有 AI 重写能力，但语义改为「重新生成本段建议与修改稿」。请求携带当前段落原文、全文段落上下文、作文配置和教师可选要求；返回结果只能更新同一个段落 ID。全文重新生成必须返回当前 OCR 的完整段落覆盖。

页面不提供可见的技术说明、颜色图例或使用教程。裁图缺失、报告过期或段落覆盖不一致时，页面在对应段落显示可操作错误，并禁止教师复核和导出。

## A4 纵向交付版式

PDF 和 DOCX 使用同一组版式令牌：

- 页面：A4 纵向，左右边距 `18 mm`，上下边距 `16 mm`。
- 正文颜色：`#171717`；改动颜色：`#C91F32`；建议底色：`#FFF0BD`。
- 文档标题：黑色楷体 `16 pt`，居中，不使用装饰线或标题卡片。
- `【第 X 段】`、`【修改建议】`、`【修改后段落】`：黑色常规字体 `11 pt`。
- 建议正文：黑色常规字体 `10.5 pt`，使用真实编号列表。
- 修改后段落：楷体 `11.5 pt`；原文黑色，新增和替换文字红色，删除文字红色删除线。
- 段落裁图：使用与 OCR 坐标一致的标准化图片版本，按区域四周增加 `1%` 页面尺寸的安全留白并裁剪到页面边界，避免切掉笔画。
- 不使用蓝色段落标题，不把普通页面区块做成卡片，不输出说明性图例。

每个自然段是一个连续逻辑单元。分页遵循以下规则：

- 标题必须与其后的第一张裁图同页。
- 建议标题至少与第一条建议同页；修改后段落标题至少与两行正文同页。
- 一个完整段落单元能放入当前页时不拆分；剩余空间不足时移到下一页。
- 单元本身超过一页时允许拆分，并在后续页显示 `【第 X 段（续）】`、`【修改建议（续）】` 或 `【修改后段落（续）】`。
- 不为强行保持整个单元同页制造参考稿中的大面积空白。

## 共享交付模型

导出前构建与文件格式无关的交付数据：

```ts
interface DeliveryParagraph {
  paragraphNumber: number;
  crops: Array<{
    pageIndex: number;
    bytes: Uint8Array;
    width: number;
    height: number;
  }>;
  suggestions: ParagraphSuggestion[];
  revisionRuns: RevisionRun[];
}

interface DeliveryDocument {
  title: string;
  studentName: string;
  paragraphs: DeliveryParagraph[];
}
```

构建器逐页读取同源受保护图片，按 OCR 区域在浏览器 Canvas 中裁剪并输出嵌入字节。图片按顺序处理并及时释放对象 URL 和临时 Canvas，避免批量导出同时展开全部原图占满内存。

PDF 渲染器继续使用现有浏览器端 `jsPDF`，改为 A4 纵向动态分页。每个 PDF 页面先绘制到高分辨率 Canvas，再作为页面图像写入 PDF，以保持中文字体、底色和删除线一致。

DOCX 渲染器使用成熟的 OOXML 生成库创建 Word 文档：

- 使用真实段落和真实编号列表，不用表格包装普通文字。
- 裁图以内嵌图片写入，不使用临时 URL 或远程链接。
- 建议区通过连续段落底纹形成浅橙色区域。
- 修改稿按 `RevisionRun` 生成独立 `TextRun`，设置楷体、颜色和删除线。
- 设置图片替代文字和明确的 East Asia 字体，保证 Windows Word、macOS Word 和 LibreOffice 有合理回退。

DOCX 中的建议和修改稿可以继续编辑；编辑后 Word 不会自动重算红黑差异，这是下载后独立文档的正常行为。

## 导出交互与状态

详情页把单一「导出 PDF」改为「导出」菜单，包含：

- `PDF`
- `Word (.docx)`

两种导出都沿用当前流程：先校验报告；未复核或存在未保存修改时，先保存并完成教师复核；再执行服务端导出资格检查；生成并下载成功后调用现有「标记已导出」接口。任一格式成功交付都可进入现有「已导出」状态，历史详情仍允许再次导出另一种格式。

批量导出清单同样提供 PDF 和 Word 两种格式。多篇 Word 导出生成 ZIP，每篇包含一个 `.docx`；多篇 PDF 继续生成 ZIP。批量任务按篇顺序生成，全部文件写入 ZIP 后再触发下载，成功后逐篇标记已导出。

文件名统一为：

```text
作文批改-<题目>-<学生姓名>.pdf
作文批改-<题目>-<学生姓名>.docx
作文批改批量导出-PDF.zip
作文批改批量导出-Word.zip
```

文件名继续移除系统不允许的字符并限制长度。DOCX 文档属性不写入模型名称、API Key、内部路径或教师账号；作者使用产品名称，不硬编码具体教师姓名。

## API、存储与兼容

- 作文详情 API 的 `ocr` 增加段落文本和裁剪片段；原始 `blocks` 继续留在服务端。
- OCR 编辑接口从逐页文本升级为逐段文本，并继续使用期望 `ocrRevision` 防止覆盖冲突。
- 新增逐段重写接口；旧 `sample-paragraphs` 重写接口只服务旧报告，不用于新报告。
- 报告和 OCR 都存为 JSON；使用 v1/v2 联合 Schema 后不需要新增 D1 列。
- DOCX 和云端浏览器 PDF 都按需在浏览器生成，不在 D1 或 R2 新增文档缓存。
- 本机服务端 PDF 打印页同步使用新纵向版式，并推进 PDF 版式发布日期，使旧缓存自动失效。

旧报告兼容策略：

- 旧 `sampleParagraphs` 报告继续可读，页面显示「旧版示范段落报告」。
- 旧报告不能导出为新 DOCX，也不能用旧数据伪造逐段 PDF；用户需要执行一次完整重新分析，生成 OCR v2 和逐段报告。
- OCR v1 没有自然段区域，因此从旧报告升级时必须重新调用视觉模型，不能误用「仅内容重新生成」。
- 已经生成或下载的旧文件不删除；重新分析后按现有规则清空教师复核状态并生成新报告。

## 错误处理

- OCR 段落为空、编号不连续、跨页关系无效或坐标越界：判定视觉模型结果无效，不调用内容模型。
- 内容模型遗漏、重复或打乱段落 ID：尝试一次结构修复；仍失败则保留 OCR 并显示内容模型错误。
- OCR 修改后报告过期：继续允许查看旧报告，但禁止复核和导出，直到重新生成成功。
- 任一段没有裁图、建议字段不完整或修改稿为空：在对应段显示错误并禁止导出。
- 原图加载或 Canvas 裁剪失败：不生成半份文件，不标记已导出，提示具体页码和段落号。
- DOCX 或 PDF 生成失败：保留教师当前编辑内容和已复核状态，不调用「标记已导出」。
- 批量导出某篇失败：停止生成并保留整个待导出清单，不提前标记任何尚未成功交付的记录。
- 浏览器内存不足：显示可重试错误，建议减少单次批量数量；实现不得静默降低图片清晰度或丢段。

## 测试策略

### OCR 与报告契约

- OCR v2 接受连续自然段和合法单页、跨页片段，拒绝空段、断号、越界、错误页码和无片段段落。
- 视觉适配器排除标题和身份字段，只把正文自然段写入 `paragraphs`。
- 内容模型请求包含段落 ID 和文本，不包含图片、坐标、签名 URL 或 Base64。
- 逐段报告必须完整覆盖 OCR 段落，拒绝遗漏、重复、乱序和未知 ID。
- 「保留」建议及普通建议都必须包含非空的问题、动作和示例。
- OCR v1 和旧报告可读，但不能通过新格式导出资格校验。

### 差异模块

- 新增文字为红色，删除文字为红色删除线，替换同时保留红色旧字和新字。
- 只改标点时文字不标红，新增标点为黑色，删除标点不显示删除线。
- 句子或短语只调序时在新位置保持黑色，旧位置不显示重复删除。
- 重复汉字、多处修改、换行、表情和组合字符不会错位或丢字。
- 教师编辑修改稿后差异立即更新，保存和重新加载后结果一致。

### 页面与交互

- 每段严格按「原文裁图 → 修改建议 → 修改后段落」展示。
- 跨页段落显示多个连续裁图；图片与段落 ID 不串段。
- 建议列表可编辑，保留项可正常保存，修改稿使用楷体红黑预览。
- 旧报告、过期报告、缺裁图报告都不能完成教师复核或新格式导出。
- 导出菜单在桌面和移动端不溢出，不遮挡保存、重写和审核操作。

### PDF 与 DOCX

- PDF 为 A4 纵向，颜色、楷体、底色、删除线和裁图均符合版式令牌。
- DOCX 包含内嵌裁图、真实列表、可编辑建议和可编辑修改稿，不包含远程图片关系。
- DOCX 的删除和新增 Run 使用正确颜色，删除 Run 设置删除线，标点 Run 保持黑色。
- 长建议、长修改稿、跨页段落和 1–4 页作文不会发生裁切、重叠或整页异常空白。
- 单篇和批量 PDF、Word 均执行教师复核与导出资格校验；失败时不提前标记已导出。
- 用 LibreOffice 渲染生成的 DOCX，逐页检查缺字、字体回退、图片比例、底色连续性和分页。

### 安全与回归

- 详情 API 不返回 OCR 原始文字块，不泄露其他租户图片或段落坐标。
- 文件名和文档属性不包含模型配置、密钥、内部存储路径或未经允许的身份信息。
- 现有等级、四维诊断、家长反馈、图片批注、OCR 过期判断和教师复核流程继续通过。
- 新旧报告联合 Schema 在本机 SQLite 与 Cloudflare D1 读取路径中行为一致。

## 验收标准

- 新分析生成的每个学生自然段都有正确原文裁图、至少一条具体建议和完整修改稿。
- 网页、PDF 和 DOCX 都严格使用「原文裁图 → 修改建议 → 修改后段落」顺序。
- 修改稿中只有增、删、换文字为红色；删除有删除线；调序文字和标点保持黑色。
- 已写得好的段落显示「保留」并说明可验证的优点。
- 跨页自然段不会被错误拆成两个报告段落，导出时按顺序显示全部裁图片段。
- PDF 和 DOCX 均为 A4 纵向，建议区为浅橙色，修改稿为楷体，页面无重叠、裁切和异常大空白。
- DOCX 的建议和修改稿可编辑，学生原文图片完整嵌入，离线打开不丢失。
- 单篇和批量导出都可选择 PDF 或 Word，并继续服从教师复核、版本和租户权限规则。
- 旧报告不会被伪转换；完成一次完整重新分析后可使用新格式。
- 内容模型从未接收作文图片或坐标，任何模型错误都不会产生不完整交付文件。

## 实施顺序

1. 建立 OCR v2 自然段契约、视觉模型提示与跨页校验。

3. 建立确定性差异模块及其完整边界测试。
4. 调整 OCR 编辑器、逐段复核编辑器和 AI 重写接口。
5. 建立共享交付模型和图片裁剪流程。
6. 将 PDF 改为 A4 纵向逐段分页，并同步本机打印页。
7. 增加单篇和批量 DOCX 生成与导出菜单。
8. 完成组件、浏览器、DOCX 渲染、PDF 视觉、隐私、构建和回归验证。
