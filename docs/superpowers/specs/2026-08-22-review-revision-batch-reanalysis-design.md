# 不合适退回修改与按最新框架批量重分析设计

## 背景

批量审核页目前只支持教师修改报告后确认通过。遇到 AI 报告不合适时，教师只能离开连续审核流程，再到单篇复核页补充观点并重新分析，无法一边退回后台修改一边继续审核下一篇。

历史首页已经支持多选作文，但多选能力只用于批量导出。教师更新了某个题目的批改框架后，无法让此前同题作文统一按最新框架重新分析，也无法在提交前确认哪些作文能匹配框架、哪些会被跳过。

现有分析任务已经支持 `content_only` 模式、教师补充意见和后台队列；保存的题目框架位于 `saved_assignments`。本次改造复用这些能力，不重新执行 OCR，也不增加新的数据库字段或外部服务。

## 目标

- 在批量审核页增加「不合适」操作，收集「为什么不合适」和「应该怎么改」。
- 后台重新生成报告与批注，提交成功后立即切换下一篇，不等待 AI 完成。
- 修改完成的作文重新进入教师待审核队列，不能绕过教师确认直接导出。
- 在历史首页基于现有多选状态，预览并提交「按最新框架重新分析」。
- 每篇作文按当前教师名下、题目同名的最新保存框架独立匹配。
- 批量操作允许部分成功，明确列出跳过原因，并保留跳过项的选择状态。
- 所有接口保持教师数据隔离、版本校验和原子状态更新。

## 非目标

- 不重新识别作文图片，不修改作文原图或 OCR 文本。
- 不增加模糊题目匹配、别名、人工选择框架或跨教师共享框架。
- 不自动把 AI 修改结果标记为教师审核通过。
- 不保存单独的退回历史记录，不新增退回原因数据表。
- 不扩大现有首页多选的批量导出数量限制；20 篇上限只约束本次批量重分析。
- 不让教师意见覆盖、补写或虚构学生原文中不存在的关键事实。

## 核心规则

### 不合适退回修改

教师必须同时填写「为什么不合适」和「应该怎么改」，两项分别去除首尾空格后不能为空，每项最多 500 个字符。提交时携带当前作文的 `expectedRevision`。服务端只有在作文属于当前教师、版本一致、当前 OCR 有效且没有活动分析任务时，才创建 `content_only` 任务。

提交成功表示后台任务已经可靠入队，不表示 AI 已完成。前端立即从当前待审核队列移除该作文并切换到预取的下一篇。任务成功后，新报告的 revision 增加，`teacherReviewedAt` 保持为空，作文重新进入待审核队列；教师仍需再次审核。

教师意见只用于指出报告问题和修改方向。模型必须以可辨认的学生原文为事实边界：意见与原文冲突时以原文为准；缺少原文依据时不得发明经历、人物、时间、地点或物品。

### 按最新框架批量重分析

教师从历史首页选择 1 至 20 篇作文后，必须先查看服务端生成的预览，再确认提交。搜索条件只影响可见列表；当前选中的隐藏作文仍参与预览和数量计算。

框架匹配使用作文当前 `config.title` 与保存框架标题去除首尾空格后的精确匹配，不做包含匹配、大小写折叠或语义匹配。只查询当前教师名下的 `saved_assignments`。现有「教师 + 标题」唯一约束保证同名框架只有一条；再次保存同一标题就是更新该记录及其 `updatedAt`，因此它就是该题目的最新框架。

每篇匹配成功的作文使用确认时仍然有效的最新框架更新 `config`，复用当前 OCR 创建 `content_only` 任务。某篇作文不满足条件时只跳过该篇，不阻断其他有效作文。

## 页面与交互

### 批量审核页

底部固定操作区在「审核通过并进入下一篇」旁增加次级危险操作「不合适」。按钮只在当前作文及报告可用、页面未执行其他提交时启用。

点击后打开聚焦输入界面：

- 桌面端使用居中对话框，宽度受视口约束，不嵌套在其他卡片中。
- 移动端使用底部面板，内容可滚动，操作按钮始终可达且不遮挡输入框。
- 两个文本域显示当前字符数与 500 字上限。
- 主操作为「提交后台修改并继续」，次操作为「取消」。
- 两项都通过本地校验后才允许提交；服务端重复执行相同校验。

提交期间只锁定对话框操作。成功后关闭输入界面，从队列移除当前作文，并使用现有预取缓存立即显示下一篇；没有下一篇时显示队列完成状态。提交失败时保留对话框、两项输入和当前作文，不切换队列。

如果当前报告存在未保存编辑，点击「不合适」时先明确提示这些编辑不会被保存；教师取消则保留编辑，确认后再进入退回表单。退回请求只提交原因和修改要求，不隐式保存本地报告编辑。

页面保存本次会话提交成功的后台任务 ID 并轮询现有任务状态。任务成功后刷新待审核队列，使修改完成的作文无需整页刷新即可重新出现；任务失败时不伪装成待审核项，作文在首页显示现有「分析失败」状态。离开页面后不依赖浏览器继续任务，后台队列照常执行；下次进入批量审核页会从服务端读取最新队列。

### 历史首页

现有批量操作区增加「按最新框架重新分析」按钮。按钮在没有选择、正在执行其他批量动作或选择超过 20 篇时禁用；超过上限时显示「每次最多重新分析 20 篇」，但不改变已有选择，以免影响批量导出。

点击按钮先请求预览并打开确认界面。预览按匹配框架标题分组，展示：

- 框架标题、最后更新时间和将使用该框架的作文数量。
- 每篇作文的学生姓名、题目和当前 revision。
- 被跳过的作文及稳定、可读的原因。
- 当前总选择数、可提交数和跳过数。

只有至少一篇可提交时才启用「确认重新分析」。确认响应允许部分成功：

- 已成功创建任务的作文进入「分析中」，并从首页选择集合中移除。
- 被跳过的作文保持选中，包括当前搜索条件下不可见的项目。
- 页面刷新作文数据，同时显示成功数和逐篇跳过原因。
- 关闭预览不改变选择状态。

确认期间列表选择与其他批量按钮暂时锁定，防止同一个选择集并发提交。预览不是锁；确认接口必须重新校验所有数据。

## API 设计

### 单篇退回接口

```text
POST /api/reviews/:id/revision-request
```

请求：

```json
{
  "expectedRevision": 7,
  "reason": "报告把两个人物的行为混在了一起。",
  "changeRequest": "按原文人物称呼重新梳理事件顺序，并改写建议。"
}
```

响应返回分析任务视图和 `newlyQueued`。正常成功必须创建本请求对应的新任务；接口不会把其他活动任务当作本次成功，因此检测到活动任务时返回冲突。

服务端校验：

- 当前会话已认证，作文属于当前教师；跨教师 ID 与不存在 ID 使用相同的未找到响应。
- `expectedRevision` 是非负整数并与当前 revision 相等。
- 两个文本字段去除首尾空格后长度为 1 至 500。
- 作文未删除，图片数量有效，当前 OCR checkpoint 的 `sourceRevision` 等于 `imageRevision`。
- 当前作文没有 `queued` 或 `running` 的分析任务。

教师意见按有标签的纯文本写入现有 `analysis_jobs.teacher_guidance`：

```text
[不合适原因]
<reason>
[修改要求]
<changeRequest>
```

两个输入各 500 字加标签后会超过现有 1000 字应用层限制，因此内部任务校验上限调整为 1100 字；单篇复核页现有「老师补充观点」输入仍保持 1000 字。数据库字段已经是 `TEXT`，无需迁移。

本机 SQLite 在数据库事务内、Cloudflare D1 在单个原子 batch 内完成：创建 `content_only` 任务、把作文设为 `analyzing`、写入 `analysisRunId`、清空 `teacherReviewedAt` 并更新时间。任一写入未满足版本条件时不得留下任务或半更新状态。

### 批量预览接口

```text
POST /api/reviews/batch-reanalysis/preview
```

请求：

```json
{
  "reviewIds": ["review-1", "review-2"]
}
```

`reviewIds` 必须是去重后的 1 至 20 个非空 ID。重复 ID 返回参数错误，避免界面数量和服务端结果不一致。

响应包含：

```json
{
  "matched": [
    {
      "reviewId": "review-1",
      "studentName": "小明",
      "title": "难忘的一天",
      "expectedRevision": 7,
      "assignmentId": "assignment-1",
      "assignmentUpdatedAt": "2026-08-22T09:30:00.000Z"
    }
  ],
  "skipped": [
    {
      "reviewId": "review-2",
      "title": "我的周末",
      "code": "FRAMEWORK_NOT_FOUND",
      "reason": "没有找到同名的已保存题目框架"
    }
  ]
}
```

预览只读，不修改作文或创建任务。除了匹配框架，它还检查当前 OCR、活动任务、作文状态和所有权，把当时不能提交的作文直接列入 `skipped`。它按输入 ID 顺序返回项目，前端再按 `assignmentId` 和标题分组展示。跨教师或已删除记录使用 `REVIEW_NOT_FOUND`，不能返回其学生姓名、标题或其他信息。

### 批量确认接口

```text
POST /api/reviews/batch-reanalysis
```

请求提交预览返回的确认字段：

```json
{
  "items": [
    {
      "reviewId": "review-1",
      "expectedRevision": 7,
      "assignmentId": "assignment-1",
      "expectedAssignmentUpdatedAt": "2026-08-22T09:30:00.000Z"
    }
  ]
}
```

确认接口不信任客户端传入的题目、框架内容或跳过结论。它重新读取当前教师的作文与保存框架，重新执行标题匹配，并校验作文 revision、框架 ID 和框架更新时间仍与预览一致。若预览后框架更新、删除或换成另一条记录，该篇返回 `FRAMEWORK_CHANGED`，要求重新预览。

每一篇作文独立执行原子提交，批次本身不做全有或全无事务，以支持部分成功。单篇原子操作包括：

1. 再次验证所有权、可用状态、当前 OCR 和无活动任务。
2. 把作文 `config` 替换为匹配框架的完整配置。
3. revision 增加 1，表示配置和可导出内容已失效。
4. 清空 `teacherReviewedAt`、`pdfFilename`、`pdfPath`、`pdfRevision` 和 `exportedAt`。
5. 把作文设为 `analyzing`，关联新任务并创建 `content_only` 分析任务。

旧报告与旧批注在后台分析期间作为失败回退数据保留，但由于状态和教师审核时间已失效，不能导出。任务成功时沿用现有流水线原子替换报告与批注，并再次增加 revision；任务失败时首页显示分析失败，旧内容不能被误判为按新框架完成的报告。

响应按请求顺序返回：

```json
{
  "submitted": [
    { "reviewId": "review-1", "jobId": "job-1", "revision": 8 }
  ],
  "skipped": [
    {
      "reviewId": "review-2",
      "code": "REVISION_CONFLICT",
      "reason": "作文已更新，请重新预览"
    }
  ]
}
```

## 状态与错误处理

稳定跳过或冲突代码至少覆盖：

- `FRAMEWORK_NOT_FOUND`：没有当前教师名下的同名保存框架。
- `FRAMEWORK_CHANGED`：预览后框架被更新、删除或替换。
- `REVIEW_NOT_FOUND`：作文不存在、已删除或不属于当前教师。
- `REVISION_CONFLICT`：作文 revision 与预览或退回请求不一致。
- `OCR_NOT_CURRENT`：没有 OCR，或 OCR 不对应当前图片 revision。
- `ANALYSIS_ACTIVE`：已有排队中或运行中的任务。
- `REVIEW_UNAVAILABLE`：作文处于删除中、空草稿或其他不可分析状态。

全局参数错误（未认证、空数组、重复 ID、超过 20 篇或无效 JSON）使用对应 HTTP 错误终止请求。确认阶段的单篇业务变化进入 `skipped`，其余项目继续提交。

单篇退回发生 revision 冲突时，输入内容继续保留，并提示教师刷新当前作文后再判断。批量确认发生部分冲突时，成功项不回滚；冲突和其他跳过项保持选择，方便重新预览。

同一作文不能由单篇退回和批量重分析同时创建任务。数据库中的活动任务唯一索引继续作为最终并发保护；服务层的预检查用于返回清晰错误，但不能替代数据库约束。

## 服务与代码边界

- 纯函数负责规范化标题、匹配最新框架、格式化教师意见、生成稳定跳过结果；这些函数不访问数据库。
- 本机服务负责 SQLite 事务、版本条件更新和任务创建。
- Cloudflare 适配器负责等价的 D1 查询与原子 batch，Worker 路由只做认证、解析和错误映射。
- 页面组件只管理选择、预览、对话框和任务轮询，不在浏览器中逐篇调用现有分析接口。
- 两个部署路径共享请求与响应 Schema、最大批量数和错误代码，避免本机测试通过而线上行为不同。

专用批量接口是必要边界：浏览器请求扇出无法在确认时统一重新匹配最新框架，也难以稳定表达部分成功、租户隔离与每篇原子更新。

## 数据存储

本次不增加数据库迁移。

- 退回原因和修改要求保存到现有 `analysis_jobs.teacher_guidance`，随任务保留。
- 最新框架来自现有 `saved_assignments.config` 和 `updated_at`。
- 作文采用现有 `reviews.config`、revision、审核状态、PDF 元数据与分析状态字段。
- 任务采用现有 `analysis_jobs` 表和 `content_only` 模式。

不增加永久的「不合适次数」或退回历史视图。任务记录能够支持当前问题排查；如果以后需要教学统计，再单独设计审计数据模型。

## 测试策略

### 纯函数与 Schema

- 标题只做首尾空格清理后的精确匹配，不误用学生姓名或模糊匹配。
- 同一标题再次保存后匹配更新后的唯一框架，并使用新的 `updatedAt`。
- 两个 500 字字段都能格式化并通过 1100 字内部任务上限；空白或超长字段被拒绝。
- 预览和确认请求限制 1 至 20 个唯一 ID。
- 所有跳过代码映射为稳定、可读且不泄露数据的文案。

### SQLite 与 D1

- 单篇退回在版本一致时原子创建任务并撤销教师审核；冲突时两者都不写入。
- 缺少当前 OCR、活动任务、删除中作文和跨教师访问均被拒绝。
- 批量确认按最新匹配框架更新完整 `config`，增加 revision，清空审核与 PDF 状态并创建任务。
- 任一单篇原子操作失败不留下半更新状态，且不回滚同批已提交的其他作文。
- 预览后作文或框架变化会跳过，不使用客户端旧数据。
- 旧报告和批注保留为失败回退，但在审核状态失效后不能导出。

### API 与 Worker

- 本机 Route Handler 和 Worker 对单篇退回、批量预览、批量确认返回等价结构。
- 覆盖无效 JSON、字段长度、重复 ID、超过 20 篇、无匹配框架和部分成功。
- 后台队列收到的任务都是 `content_only`，复用当前 OCR 并带有正确框架或教师意见。
- AI 成功后作文回到 `ready_for_review` 且 `teacherReviewedAt` 为空；失败后首页显示分析失败。
- 并发提交同一作文最多只有一个活动任务。

### 组件与浏览器验收

- 桌面对话框和移动底部面板都要求两个字段，显示字符计数，并在失败后保留输入。
- 单篇提交成功立即显示预取的下一篇，不出现整页加载。
- 后台任务成功后刷新队列，修改后的作文可以再次进入批改。
- 首页预览按框架分组，显示可提交与跳过项目，确认前不修改任何数据。
- 成功项取消选择，跳过项及不可见选中项保持选择。
- 选择超过 20 篇时不影响导出，但不能发起重分析。
- 在 1440 x 1000 和 390 x 844 视口验证无横向溢出、按钮不遮挡输入与正文、最长错误文案不溢出。

### 完整验证

- 运行 lint、完整 Vitest、Cloudflare Worker 测试和生产构建。
- 使用 Playwright 覆盖单篇退回、立即切换、任务完成回队列、批量预览和部分成功。
- 对桌面和移动视口保存截图并检查控制台错误、网络失败与页面横向滚动。

## 兼容与发布

- 不需要数据库迁移，现有作文、框架和任务记录继续兼容。
- 先发布后端接口与共享 Schema，再发布使用新接口的页面；同一次正式部署中完成即可。
- 发布前使用测试账号准备：可匹配框架、无匹配框架、旧 OCR、活动任务和 revision 冲突数据。
- 发布后验证单篇退回即时切换、任务成功回队列、任务失败状态、批量部分成功、选择保留和导出阻断。
- 生产验证通过后同步 GitHub `main` 与 Cloudflare 部署版本，并记录 commit 与 deployment ID。
