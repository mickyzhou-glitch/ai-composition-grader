# 示范作文字数容错设计

## 背景

`teacher01` 有 36 篇待复核作文需要按最新批改能力重新分析。线上任务全部使用目标 600 字、5 段的题目配置。首轮入队后，已消费的 24 篇全部失败，其中 20 篇为 `AI_INVALID_RESPONSE_sample_paragraphs`，另外 4 篇为整份报告修复后的 Schema 错误。剩余 12 篇已暂停在 Cloudflare Queue 中。

现有校验要求示范作文各段 `text` 的汉字总数必须为 600–660。内容模型已能返回完整报告，但对精确字数的遵循不稳定；当系统要求重写整份 JSON 时，还可能损坏原本正确的字段。部分作业的 `structureRequirements` 已经为每一段填写独立的建议字数，这类要求不能再被总字数范围覆盖。

## 决策

示范作文的字数校验按以下优先级执行：

- 当 `structureRequirements` 按段提供了完整的建议字数范围时，逐段使用这些范围（含边界），不再校验总字数。
- 没有完整分段范围时，才使用总量兜底：参考下限为 `targetCharacters - 50`（最低为 1），上限为 `targetCharacters + 100`；低于参考下限也不拒绝结果。

因此，没有分段范围且目标为 600 字时，模型以 550–700 个汉字为目标参考范围，服务端只拒绝超过 700 个汉字；有分段范围时，模型提示词、生成结果校验、单段重写和全文重写都按同一组分段范围执行。所有入口继续共用同一个 `resolveSampleWritingRequirements` 结果，避免规则漂移。

## 保持严格的规则

- `sampleParagraphs` 必须恰好符合题目配置的段落数；当前线上数据仍为 5 段。
- 每段的 `title`、`text` 和 `suggestion` 必须是非空字符串。
- JSON Schema、题目结构覆盖、家长反馈、等级和批注页码等现有校验不变。
- 不通过截断、拼接填充词或修改数据库报告来伪造合格结果；低于参考下限时直接保留真实内容。

## 定向修复

线上验证表明，仅将范围放宽到 550–700 后，内容模型在“重写整份报告”的修复请求中仍连续返回不合格范文。因此，当初次结果已通过 Schema，且唯一已知错误是 `sample_paragraphs` 时，修复请求只返回正文文本数组，保留初次报告中的标题和修改建议。系统将正文合并回初次报告，最多再依据实测字数进行一次扩写或精简，然后重新执行整份报告语义校验。

其他错误继续使用原有完整报告修复流程。该方案不修改数据库 Schema，也不改动前端。

## 线上恢复

1. 编写回归测试，确认 549 个汉字正常返回，550 和 700 个汉字正常返回，701 个汉字被拒绝。
2. 修改共享字数规则和范文定向修复流程，运行 AI 适配器测试、全量单元测试、Lint 和生产构建。
3. 部署 Cloudflare Worker，确认线上配置已生效。
4. 恢复队列中尚未消费的 12 篇。
5. 对已失败的 24 篇重新提交 `content_only` 任务，复用现有 OCR。
6. 持续核对 36 篇的成功、运行中和失败数；失败项仅针对原因重试，不重复处理已成功项。

## 验收标准

- 没有分段范围且目标 600 字时，提示词使用 550–700 个汉字作为目标参考范围，服务端只拒绝超过 700 个汉字。
- 有分段范围时，每一段都满足教师填写的边界，即使合计超过 700 字也不被误拒绝。
- 5 段要求和所有其他核心校验保持不变。
- 36 篇作文都产生新的待复核报告，每篇对应的最新分析任务为 `succeeded`。
- 临时操作会话在任务提交后立即撤销。

## 回滚

如果新版部署后出现新的系统性错误，再次暂停分析队列，将 Worker 回滚到部署前版本，保留已完成的报告，只重试未成功任务。
