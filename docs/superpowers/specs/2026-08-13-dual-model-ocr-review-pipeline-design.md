# 双模型 OCR 与作文批改流水线设计

## 背景

当前系统使用一套 OpenAI 兼容配置，由同一个模型在一次请求中同时读取作文图片、生成图片批注、评价作文并生成范文和家长反馈。这种实现把视觉识别和作文内容生成耦合在一起，无法为两类任务分别选择模型，也无法在内容生成失败或教师修正识别文本后复用已经完成的识图结果。

本次优化将分析流程拆成「视觉模型识别」和「内容模型批改」两个连续阶段。两个模型拥有完全独立的服务地址、模型名称和 API Key，可以来自不同的 OpenAI 兼容服务商。

## 目标

- 视觉模型只读取作文图片，输出逐页原文、文本块坐标、页面可读状态和警告。
- 内容模型只接收结构化 OCR 文本、作文要求、学生姓名和教师补充意见，不接收作文图片。
- 首次分析自动连续完成识图和内容生成，不要求教师中途确认。
- 保存 OCR 检查点，使内容生成失败后可以从第二阶段继续。
- 教师可以在报告页检查并修改识别原文，然后只重新调用内容模型。
- 继续支持现有的等级、诊断、范文、家长反馈和图片批注能力。
- 无法可靠定位的批注不得错误绘制到作文图片上。

## 非目标

- 不引入 Dify、Coze 等外部工作流平台。
- 不把 OCR 和内容生成拆成两个独立 Queue 任务。
- 不更换现有 Cloudflare D1、R2 和 Queues 基础设施。
- 不支持非 OpenAI Chat Completions 兼容协议；不同协议需由供应商网关转换，或在后续增加新的客户端适配器。
- 不在本次优化中增加 OCR 版本历史或报告版本对比。
- 不尝试为教师手工新增的文字伪造图片坐标。

## 总体架构

单个分析任务内部按两个模型阶段顺序执行，并在阶段之间保存 OCR 检查点：

```text
上传作文图片
    ↓
读取与校验当前图片版本
    ↓
视觉模型：逐页 OCR + 文本块坐标
    ↓
保存 OCR 检查点
    ↓
内容模型：评价、诊断、范文、家长反馈、批注锚点
    ↓
程序将批注锚点映射到 OCR 文本块坐标
    ↓
校验并原子保存完整报告
```

新增或调整以下职责边界：

- `VisionOcrAdapter`：接收按页排序的作文图片，调用视觉模型并返回经过 Schema 校验的 OCR 结果。它不生成评分、建议、范文或家长反馈。
- `CompositionReviewAdapter`：由现有 `OpenAIReviewAdapter` 演进而来，接收 OCR 文本和业务上下文，生成报告与批注锚点。范文重写、优点或问题重写、整篇范文重写和题目要求生成也统一使用内容模型。
- `AnalysisPipeline`：在现有异步分析任务中编排两个阶段，决定是否读取已有 OCR、调用哪个适配器、更新进度、映射批注和保存最终结果。
- `AnnotationMapper`：将内容模型返回的页码与 `anchorText` 映射到视觉模型文本块，并生成现有报告契约所需的归一化坐标。

两个模型的 API Key 只在 Worker 服务端读取或解密。浏览器只能获知对应密钥是否已经配置，不能读取完整密钥。

## 模型配置

系统维护两个独立配置槽位：

```ts
type AiModelRole = "vision" | "content";

interface AiModelRuntimeConfig {
  baseUrl: string;
  model: string;
  apiKey: string;
}
```

D1 `settings` 表从 `id = 1` 的单条共享配置重建为以 `role` 为主键的配置表，`role` 只允许 `vision` 和 `content`。每条配置独立保存 `base_url`、`model`、`encrypted_api_key` 和 `updated_at`。迁移时，现有配置复制到两个角色，保证升级后旧部署仍能工作；管理员之后可以分别替换。

环境变量密钥同样分为 `VISION_AI_API_KEY` 和 `CONTENT_AI_API_KEY`。已加密存入 D1 的角色密钥优先于环境变量。旧的 `AI_API_KEY` 仅在迁移兼容期作为两类角色都未配置时的回退值，并在文档中标记为废弃。

设置 API 返回：

```ts
interface DualModelSettingsView {
  vision: {
    baseUrl: string;
    model: string;
    keyConfigured: boolean;
  } | null;
  content: {
    baseUrl: string;
    model: string;
    keyConfigured: boolean;
  } | null;
}
```

保存和测试接口必须携带 `role`，服务端只读写指定角色，不能覆盖另一角色。视觉模型连接测试发送一张最小测试图片；内容模型连接测试发送要求返回 JSON 的纯文本请求。

## OCR 数据契约

OCR 检查点使用带版本的结构：

```ts
interface OcrCheckpoint {
  version: 1;
  sourceRevision: number;
  ocrRevision: number;
  editedAt: string | null;
  pages: Array<{
    pageIndex: number;
    text: string;
    readable: boolean;
    warnings: string[];
    blocks: Array<{
      text: string;
      x: number;
      y: number;
      width: number;
      height: number;
    }>;
  }>;
}
```

约束如下：

- `pages` 数量必须与当前作文图片数量一致，`pageIndex` 从 `0` 连续递增。
- 坐标和尺寸相对于整页归一化到 `0..1`，文本块不得超出页面边界。
- `text` 是按阅读顺序合并的逐页正文，也是教师可编辑、内容模型实际使用的字段。
- `blocks` 保存视觉模型原始识别文字和坐标，只用于图片定位，不因教师修改 `text` 而伪造或移动。
- `sourceRevision` 绑定产生该 OCR 的图片版本。它只反映影响图片内容或顺序的修订，不能被纯 OCR 文本编辑推进。
- `ocrRevision` 是当前检查点的单调递增编辑版本。模型首次识别保存为 `0`，每次教师成功保存文本后加 `1`。
- `editedAt` 为空表示模型原始识别结果，非空表示教师修改过至少一页文本。
- OCR JSON 可以保存到 D1，但图片 Base64 仍不进入数据库。

`reviews` 需要保存 OCR 检查点及其状态，并区分「当前图片版本」与普通报告编辑产生的 `revision`。实现时新增专用的 `image_revision`，避免教师修改报告导致 OCR 被错误判定失效；同时使用 `report_ocr_revision` 记录当前报告基于哪个 OCR 编辑版本。报告过期状态由 `report_ocr_revision !== ocrCheckpoint.ocrRevision` 推导，不额外保存布尔字段。

## 内容模型输入与输出

内容模型输入包含：

- 作文题目、年级、目标字数、结构要求和评分重点。
- 学生姓名和教师补充意见。
- 每一页经过教师修正后的 `text`。
- 页面边界和页码，不包含图片 URL、数据 URL 或图片 Base64。

内容模型输出沿用现有 `EvaluationReport` 的主体字段，但图片批注在模型边界处先使用无坐标锚点：

```ts
interface ReviewAnnotationAnchor {
  pageIndex: number;
  category: "structure";
  anchorText: string;
  comment: string;
  isHighlight: false;
}
```

内容模型不得返回 `x` 和 `y`。坐标只由 `AnnotationMapper` 根据 OCR 文本块推导，防止纯文本模型虚构图片位置。

## 批注坐标映射

映射按以下规则执行：

1. 只在 `pageIndex` 指定页面内查找。
2. 对 `anchorText` 和文本块文字统一做 Unicode 规范化、空白折叠和常见全半角标点规范化。
3. 优先匹配单个文本块的完整连续文字；必要时允许匹配阅读顺序相邻的少量文本块。
4. 只有找到唯一候选时才计算坐标，使用首个匹配文本块的稳定锚点生成现有 `x`、`y` 字段。
5. 找不到候选或出现多个候选时，不生成图片批注。对应问题仍保留在文字报告的诊断或修改建议中。
6. 教师手工修改的文字如果不能在原始 `blocks` 中唯一匹配，同样不生成图片批注。

首版不使用模糊语义匹配，避免相似句和重复句造成错误定位。

## 任务编排与进度

沿用单个 `analysis_jobs` 任务和现有 Queue 消费模式，扩展进度阶段：

```text
queued
→ reading_images
→ saving_ocr
→ generating_review
→ mapping_annotations
→ validating_result
→ saving_result
→ succeeded
```

首次分析：

1. 任务获取当前图片版本和分析运行标识。
2. 没有匹配当前图片版本的 OCR 时，调用视觉模型。
3. 校验 OCR；核心正文不可读时将作文置为 `needs_better_images`，不调用内容模型。
4. OCR 成功后立即保存检查点。
5. 调用内容模型、映射批注、校验报告。
6. 再次核对运行标识、图片版本和 OCR 编辑版本，确认未过期后原子保存结果。

失败与重试：

- 视觉模型失败时不保存不完整 OCR，任务记录安全错误码。
- OCR 已保存后内容模型失败，任务标记失败但保留 OCR；重试直接从 `generating_review` 开始。
- 教师修改 OCR 后重新生成时，新建分析任务并强制复用当前 OCR，不调用视觉模型。
- 旧任务不得覆盖较新的图片、OCR 编辑或报告。保存前的版本条件检查必须失败关闭。
- 任务可记录模型角色、非敏感模型名、阶段和安全错误码，但不能记录 API Key、图片 Base64、签名图片地址或完整作文正文。

## OCR 编辑与报告一致性

报告页新增「识别原文」标签页，按图片页码展示可编辑文本。首次分析仍自动运行两个模型，教师无需先确认 OCR。

教师保存 OCR 修改时：

- 只更新页面 `text` 和 OCR 编辑版本，不修改原始 `blocks`。
- 不立即删除当前报告；保存后 `ocrRevision` 增加，系统通过版本不一致把报告标记为「基于旧原文」。
- 页面提供「重新生成批改」命令，明确说明只会调用作文内容模型。
- 新报告成功生成后原子替换旧报告，并把 `reportOcrRevision` 更新为当前 `ocrRevision`，过期状态随之消失。
- 新报告生成失败时继续保留旧报告和过期提示，避免已有结果丢失。

重新上传、裁剪、旋转或调整图片顺序时：

- 推进图片内容版本。
- 立即使旧 OCR 和旧报告失效。
- 下次分析必须重新调用视觉模型。

普通报告文字编辑不影响图片内容版本，也不使 OCR 失效。

## 页面设计

设置页分为两个同级配置区：

- 「拍照识图模型」：服务地址、模型名称、API Key、测试连接。
- 「作文内容模型」：服务地址、模型名称、API Key、测试连接。

两个配置区分别显示密钥配置状态和连接测试结果。保存其中一项时不得隐式提交另一项的空密钥。

分析等待页面显示面向教师的阶段文案：

- `reading_images`、`saving_ocr`：正在识别作文。
- `generating_review`、`mapping_annotations`、`validating_result`：正在生成批改内容。
- `saving_result`：正在保存结果。

报告页保留现有复核和导出工作区，并新增「识别原文」标签页。过期报告需要有清晰但不阻断阅读的状态提示和重新生成入口。

## API 变化

需要增加或调整以下服务端能力：

- 按 `vision`、`content` 获取、保存和测试模型配置。
- 获取当前作文 OCR 检查点；响应只返回教师所需的逐页文本和警告，不必向浏览器暴露原始坐标块。
- 使用期望版本保存 OCR 文本编辑，防止多个页面覆盖彼此。
- 基于当前 OCR 创建「仅重新生成内容」任务。
- 作文详情返回报告是否基于当前 OCR 的一致性状态。

所有写接口继续要求当前用户身份、租户所有权和乐观并发版本。

## 错误处理

对教师显示可操作的阶段错误：

- 视觉模型未配置或连接失败：提示检查「拍照识图模型」。
- 内容模型未配置或连接失败：保留 OCR，并提示检查「作文内容模型」后重试。
- 图片核心内容不可读：进入 `needs_better_images` 并展示逐页重拍建议。
- OCR 或报告不符合 Schema：返回安全的结构校验错误，不回显上游原始内容。
- OCR 编辑发生版本冲突：返回 `409`，要求刷新后重新编辑。
- 任务保存时发现图片或 OCR 已变化：取消旧结果，不覆盖新状态。

## 数据迁移与兼容

- 新增 D1 migration，把原单模型设置迁移为两个角色配置。
- 为现有作文增加 OCR 检查点、图片内容版本和报告 OCR 版本字段；旧作文这些字段为空。
- 旧作文报告继续可读和导出。只有重新分析或编辑 OCR 时才进入新流水线。
- 本机 SQLite 旧版仍需保持可编译和测试通过；它可以使用相同领域接口，但不要求与云端同时上线全部管理界面。
- 更新 `.dev.vars.example`、`worker-configuration.d.ts` 和 README 的部署说明，明确两个角色密钥。

## 测试策略

### 单元测试

- 视觉模型输出的解析、Schema 校验、页数与坐标边界。
- 内容模型请求不包含图片 URL、数据 URL 或 Base64。
- OCR 文本到批注坐标的唯一匹配、跨相邻块匹配、无匹配和歧义匹配。
- 教师修改文本后原始坐标块保持不变。
- 两个角色配置独立保存、读取、加密和回退。

### 任务与存储测试

- 首次运行依次调用视觉模型和内容模型。
- OCR 检查点保存后内容生成失败，重试不再调用视觉模型。
- 教师修改 OCR 后只调用内容模型。
- 图片上传、裁剪、旋转或排序后旧 OCR 失效。
- 报告普通编辑不使 OCR 失效。
- 旧任务不能覆盖新的图片版本、OCR 编辑版本或报告。
- 视觉模型判定不可读时不调用内容模型。

### 页面与端到端测试

- 设置页分别测试和保存两个模型。
- 报告页查看、编辑和保存逐页 OCR 文本。
- OCR 修改后显示旧报告提示，重新生成成功后清除提示。
- 重新生成失败时旧报告仍可阅读。
- 上传作文后自动完成双阶段分析；修改 OCR 后不会再次请求视觉模型。

### 隐私与安全测试

- 日志和 API 错误不包含 API Key、图片 Base64、签名图片地址或完整作文正文。
- 内容模型 mock 明确断言从未收到图片。
- 浏览器端设置响应只包含 `keyConfigured`，不回显密钥。

## 验收标准

- 视觉模型和内容模型可以配置为不同 OpenAI 兼容服务商。
- 首次上传后自动完成 OCR 和报告生成，不增加强制确认步骤。
- 内容模型的任何请求都不包含作文图片。
- OCR 成功后，内容生成失败可以复用检查点继续。
- 教师修改 OCR 后只产生内容模型调用，并基于新文本生成报告。
- 图片版本变化后绝不复用旧 OCR。
- 无法唯一映射的批注不会绘制到图片上。
- 两个模型密钥不进入浏览器、日志或数据库明文。
- 现有作文报告查看、教师复核和 PDF 导出能力不回归。

## 实施顺序

1. 建立双角色模型配置与数据库迁移。
2. 建立 OCR 领域契约、视觉适配器及其测试。
3. 将内容生成从图片输入改为 OCR 文本输入。
4. 增加 OCR 检查点、图片内容版本和批注映射。
5. 调整分析任务的阶段、重试和并发保护。
6. 增加双模型设置界面和 OCR 编辑交互。
7. 完成端到端、隐私、构建和部署验证。
