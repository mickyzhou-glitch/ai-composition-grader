# AI 作文批改助手 · 发布检查清单

给非开发同学用的短流程：改完功能后，按顺序做，避免再出现「线上有、GitHub 没有」。

正式地址：https://ai-composition-grader.mickyzhou7.workers.dev  
仓库：https://github.com/mickyzhou-glitch/ai-composition-grader

---

## 每次发布前（必做）

1. **说清楚这次改了什么**  
   用一句话写：给谁用、改了什么体验、有没有删功能。

2. **本机能跑通主流程**（登录后点一遍即可）  
   - 新建作文（照片或 Word/PDF）  
   - 能开始分析，进度会动  
   - 能打开复核页，改识别原文 / 建议  
   - 完成教师审核后，能导出 PDF 或 Word  

3. **先提交再发布**  
   - 在项目目录确认当前在 `main`  
   - 提交所有本次改动（不要提交 `.dev.vars`、密钥、学生作文）  
   - 推送到 GitHub：`main`  
   - **规则：没有推到 GitHub，就不做正式发布**

4. **需要数据库变更时**  
   - 若有新的 `migrations/*.sql`，发布前先在正式 D1 应用迁移  
   - 发布记录里写清：迁移是否已应用

---

## 发布时

5. **用正式构建发布**（不要把开发目录 `.next` 里的调试文件传上去）  
6. **记下 Worker 版本号** 和上一版本号，方便回滚  
7. **发布后立刻冒烟**（未登录 / 已登录各看一眼）  
   - 健康检查 / 登录页能开  
   - 未登录访问业务接口应被拦住  
   - 新建页、复核页能开  
   - 本次新功能点一次确认存在；已删功能确认找不到  

---

## 发布后（当天补完）

8. **写一页发布记录**（可放在 `docs/superpowers/plans/`，文件名带日期）  
   至少写：日期、正式地址、Worker 版本、改了什么、测过什么、有没有动数据库  
9. **若发布失败或异常**  
   - 先回滚到上一 Worker 版本  
   - 再查是构建问题、迁移问题，还是功能本身的问题  
10. **不要**在正式环境用真实学生作文做随便试；回归尽量用测试账号或模拟数据  

---

## 一句话口诀

**说清改动 → 本机点通 → 提交推送 → 再发布 → 冒烟 → 记版本**
